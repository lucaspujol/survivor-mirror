## Getting started

`docker compose up` applies the migrations before starting the API
(`alembic upgrade head && uvicorn ...`).

```sh
docker compose up --build                               # database + migrations + API + frontend
docker compose exec db psql -U geoemploi -d geoemploi   # psql shell
```

`DATABASE_URL` is injected by Compose. Outside the containers, the default in
`api/app/db.py` points at `localhost:5433`.

## Migrations

Run every command from `api/` (or through `docker compose exec api <command>`).

```sh
alembic upgrade head          # apply
alembic downgrade base        # revert everything
alembic current               # current revision
alembic history               # history
alembic check                 # models vs deployed schema
alembic revision --autogenerate -m "message"   # new migration
```

Always review an autogenerated file: Alembic detects neither `CHECK`
constraints nor extension changes.

Start again from an empty database:

```sh
docker compose down -v && docker compose up --build
```

## Schema

### `users`

Authentication account, shared by both profiles. Only the password **hash** is
stored.

| Column | Type | Constraints |
| --- | --- | --- |
| `id` | `bigserial` | PK |
| `email` | `text` | NOT NULL, UNIQUE |
| `password_hash` | `text` | NOT NULL |
| `role` | `varchar` | NOT NULL, CHECK `seeker` / `employer` / `admin` |
| `created_at`, `updated_at` | `timestamptz` | NOT NULL, default `now()` |

### `job_seekers`

The job seeker's professional profile, 1–1 with `users` (`user_id` is both the
primary key and a foreign key, `ON DELETE CASCADE`).

| Column | Type | Constraints |
| --- | --- | --- |
| `user_id` | `bigint` | PK, FK → `users.id` |
| `first_name`, `last_name` | `text` | NOT NULL |
| `skills` | `text[]` | NOT NULL, default `{}` |
| `experience` | `text` | nullable — free-text work experience |
| `availability` | `date` | nullable — available from |

### `employers`

Same 1–1 relationship with `users`. `activity_verified` records the Ministry's
validation of the company's activity.

### `jobs`

| Column | Type | Constraints |
| --- | --- | --- |
| `id` | `bigserial` | PK |
| `employer_id` | `bigint` | NOT NULL, FK → `employers.user_id`, CASCADE |
| `title`, `description` | `text` | NOT NULL |
| `location_address` | `text` | nullable — address sent to the Adresse API |
| `location_city` | `text` | NOT NULL |
| `location` | `geometry(Point, 4326)` | nullable — WGS84 point |
| `geocoding_source` | `text` | nullable |
| `geocoding_score` | `double precision` | nullable, CHECK between 0 and 1 |
| `geocoded_at` | `timestamptz` | nullable |
| `location_status` | `varchar` | NOT NULL, CHECK `pending` / `geocoded` / `to_verify` |

`to_verify` is the "location needs checking" state. `ck_jobs_geocoded_requires_location`
guarantees that an offer marked `geocoded` actually carries its point and its
geocoding provenance.

### `applications`

An application links a job seeker to an offer. `uq_applications_job_seeker`
rules out duplicates; `status` follows `sent` → `under_review` → `accepted` /
`rejected`.

## Indexes

| Index | Purpose |
| --- | --- |
| `uq_users_email` | login, account uniqueness |
| `ix_jobs_employer_id` | an employer's own offers |
| `ix_jobs_location` (GIST) | map search |
| `uq_applications_job_seeker` | uniqueness + an offer's applications (`job_id`) |
| `ix_applications_job_seeker_id` | a job seeker's applications |

## Geolocation and privacy

- **No user GPS position is ever stored.** Browser geolocation stays optional:
  it is only a query parameter used to centre the map, and is never persisted.
- Denying geolocation blocks nothing: a manually entered municipality is
  geocoded on the fly and used as the search position.
- No personal data beyond what the service needs: no date of birth, no national
  ID number, no home address, no banking data, no location history.

## Coordinates and projections

WGS84 (EPSG:4326) is the only projection stored. Lambert-93 (EPSG:2154),
required for administration and exports, is **computed on demand**:

- in Python: `to_lambert93()` in [`api/app/main.py`](../api/app/main.py) (pyproj);
- in SQL: `ST_X(ST_Transform(location, 2154))`, `ST_Y(...)`.

Latitude and longitude are derived from `location` (`ST_Y(location)`,
`ST_X(location)`), so they are not stored twice.

Example queries:

```sql
-- Offers within the visible map bounds
SELECT id, title, ST_Y(location) AS lat, ST_X(location) AS lng
FROM jobs
WHERE location && ST_MakeEnvelope(:west, :south, :east, :north, 4326);

-- Offers within 20 km of a search position
SELECT id, title
FROM jobs
WHERE ST_DWithin(location::geography, ST_MakePoint(:lng, :lat)::geography, 20000);

-- Administrative export in Lambert-93
SELECT id, ST_X(ST_Transform(location, 2154)) AS x, ST_Y(ST_Transform(location, 2154)) AS y
FROM jobs WHERE location IS NOT NULL;

-- Offers that need geocoding again
SELECT id, location_address, location_city
FROM jobs WHERE location_status <> 'geocoded';
```

An offer can be geocoded again at any time: update `location`,
`geocoding_source`, `geocoding_score`, `geocoded_at` and `location_status`.

## PostGIS image

The `postgis/postgis` image also installs the TIGER geocoder (US address data,
about 40 tables), topology and `fuzzystrmatch`, and adds those schemas to the
database `search_path`. GéoEmploi needs none of them, so the initial migration
drops them and resets `search_path`. Only the `postgis` extension is kept.
